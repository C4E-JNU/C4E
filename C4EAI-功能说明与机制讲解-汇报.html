Core Loop

核心链路：一次对话的生命周期

前端 sendMessage → reactAgentLoop，后端 /api/agent/stream 内跑 ReAct 工具循环，逐事件流回渲染

① 用户发送messages.js 构造消息＋附件（file_id / 图片）
→
② reactAgentLoop组装请求体：history · enabled_tools · loaded_skills · engine · max_rounds
→
③ POST /api/agent/streamSSE 长连接
→
④ ReAct 循环LLM → tool_calls → 执行工具 → 结果回填 → 再问，直到产出正文
→
⑤ 事件流回token / reasoning / tool / final
→
⑥ 渲染＋落盘推理框＋正文；存 currentBranch.messages → localStorage

⏹停止生成（前后端协同）

点 ■ → 前端 abort() 断连 → 后端 watchdog（0.4s 轮询断连）→ cancel_active_generation 置停止令牌 → 各检查点 yield stopped 并 return。避免"断了还在烧 token"。

✎续写与重新生成

继续生成：mergeInto: messageId，新内容合并进原消息框（原文＋续写＋推理同框），不新建消息。
重新生成：regenerateMessage 先 deleteMessagesAfter —— 历史不堆叠、上下文不膨胀。

上下文治理：历史只取 contextLength×2 条窗口；_build_context 内置单条 8k ＋ 总量 30 万字符兜底封顶。
Engine

双引擎设计：custom（手搓流式）为主，LangChain 备选

请求体 engine: "custom | langchain" 决定后端走 stream_agent 还是 stream_agent_lc，共享同一套系统提示词与上下文构建

Acustom 引擎（stream_agent）

  • 直接走 OpenAI 兼容 HTTP 协议，无框架依赖
  • asyncio.Queue ＋ 后台任务推送事件 → 真正的逐 token 流式
  • 子智能体可流式上屏（emit subagent_step 事件，前端 subagent_view 实时展示）
  • 检查点响应停止令牌，停止即时

BLangChain 引擎（stream_agent_lc）

  • 复用 LangChain 生态（模型抽象 / 工具绑定）
  • 事件为批处理粒度（round start / end），无逐 token 流
  • 作为对照组保留：一旦需要更复杂的 chain 编排可平滑切换

两引擎共享的底层机制（agent.py）

机制实现
系统提示词_build_system_prompt()：角色设定 ＋ 启用技能简列注入 ＋ 工具使用规范
上下文构建_build_context()：截取历史窗口；附件按 file_id 注入解析全文；图片转多模态 base64
模型兼容思考型模型兜底：max_tokens ≥ 2048、enable_thinking:false、兼容读取 reasoning_content
权限保留管理级用户可保留 permission_mode（safe / ask / full）

防上下文暴涨的封顶设计

  • read_file 单次封顶 20k 字符（READ_FILE_MAX_CHARS），截断带 next_offset 供分页续读
  • 历史窗口 contextLength×2 条 ＋ 单条 8k ＋ 总量 30 万字符兜底
  • MinerU 产物禁止整读长行大 JSON（layout.json ~2MB），只读 00_full_cleaned.md 与 00_images_map.json
教训：早期附件注入无字符上限，长行 JSON 一次数 MB 进入 state，是上下文暴涨的根因 —— 已全部封顶。

Subagent

子智能体：主 Agent 可委派的隔离执行单元

主 Agent 通过 delegate_task 工具派发任务；角色提示词预设集中在 subagent.py 的 SUBAGENT_ROLE_PROMPTS

1contradiction 矛盾发现

跨文献找互相矛盾的结论，输出证据对。

2extraction 信息抽取

从解析产物中按模板抽取结构化字段。

3verify 互证校验

对提取结果做交叉核验；互证时优先放大原图核对"图例-曲线"对应关系，防多面板颜色错配。

调度约束（防失控）

深度 = 1子智能体不能再派子智能体
→
并发 ≤ 2同时最多两个子任务
→
轮次 ≤ 4单任务最多 4 轮工具循环
→
超时 300s裸 HTTP 循环，无框架开销

流式上屏（仅 custom 引擎）

后台任务通过 asyncio.Queue emit subagent_step 事件 → 前端 subagent_view.js 实时渲染子任务步骤；LangChain 引擎退化为批处理 start/end。

典型工作流

文献挖掘场景：主 Agent 归档图像 → 派 extraction 填 schema → 派 verify 互证 → 汇总写 06_schema.json（下游对账脚本只认这个文件名）。

Knowledge

知识图谱 与 向量记忆

结构化知识走 Neo4j 图谱，非结构化走向量检索 —— 两条互补的知识通道

🕸️ Neo4j 知识图谱（结构化）

  • 图谱结构可配置；当前库内存有科研实体关系数据（历史沉淀，可扩展）
  • 配置面板填 URI/账号 → /api/neo4j/connect
  • Agent 查询套路：graph_schema 先取结构 → 生成 Cypher → execute_cypher 执行 → 基于结果作答
  • 安全：cypher 删除类操作仅 admin 可用

🧠 向量记忆（非结构化）

  • 本地 Qdrant ＋ bge-small-zh 嵌入模型（model_cache 缓存 91MB）
  • search_history：检索历史对话，"上次聊到哪了"随取随用
  • search_knowledge：检索共享库条目正文 —— 笔记与机器解析文档都进索引
  • conversation_notes：对话笔记落 workspace/users/<名>/notes.json，后端实时读取
为什么两条都要：图谱回答"A 与 B 是什么关系"这类结构化查询，精确可追溯；向量检索覆盖长文本语义模糊匹配。Agent 按问题性质自行选择工具。
Shared Hub

云端共享库：组级知识中枢

branch_id=__db__；唯一一份数据在服务器 workspace/pool/；近期重构为「文件夹树」模型

树形结构（类型 → 分组 → 条目）

📁 笔记（根文件夹）kind=note：人写的，适合直接阅读 —— 默认展示 Tab
→
📁 文档（根文件夹）kind=document：机器解析正文，文本乱但用于检索/向量索引
→
🗂️ 分组（手动管理）分组管理面板：新建 / 编辑简介 / 移动 / 删除
→
📄 条目文本 ＋ 附件，两类共用同一套 CRUD，数据结构完全一致

附件同步机制（防 404 的关键）

场景行为
云端版本上传直存服务器；共享条目 = 个人 1 份 ＋ 共享 1 份
本地版本 → 共享库/api/file/upload?source=database 代理转发到云端写 pool/uploads/，并把条目正文里的 file_id 换成云端新 id
本地读取共享附件本地找不到 → /raw /{id} /text 三接口代理到云端取
历史坑（已修）：早期只写占位符不传文件 → 云端 file_id 指向本机 id，服务器 pool/uploads 没有文件 → 云端打开 404。排查口诀：云端打不开但本地能开 = 查 pool/uploads 里有没有该 file_id。
Access Control

六级权限体系（方案 B）

实现于 backend/role_policy.py，云端 C4EAI_AUTH=1 时生效；注册默认 L1

等级云端库上传/查询改删他人数据服务器文件工具数本地千问配额身份管理
L0 游客❌❌❌限 4 个5M/日—
L1 蓝自己❌锁本人目录6 个5M/日—
L2 紫自己❌锁本人目录6 个5M/日—
L3 橙所有人❌锁本人目录6 个5M/日—
L4 红所有人❌✅ 全盘读写✅ 9 个不限—
L5 金所有人❌✅ 全盘读写✅ 9 个不限可调 L0–L4
admin所有人✅ 所有人✅ 全盘读写✅ 9 个不限授任何等级 · 可删账号

两个判据函数，不可混用

is_super(user) = L5 或 admin → 管理级（管理面板 / 全套工具 / 全盘文件）
is_root(user) = 仅 admin → 删账号 / 授 L5 / 改删他人数据
混用后果：金色会获得删账号权限，违背方案 B。

其他落地细节

· 文件沙箱 user_sandbox：L3 及以下锁本人目录，L4+ 返回 None 不锁
· 工具 filter_tools 按等级过滤；run_code / terminal 仅 admin
· admin 账号不可降级/删除；L5 不能授予 L5
· 前端 isAdmin 按 username === 'admin' 判，不按 role 字段（历史账号脏数据）

Deployment

部署、域名与前端防缓存

本地与云端同一代码库，靠环境变量与启动方式区分；改动必须「双份同步」才对全组生效

云端发布（deploy_cloud.py）

① paramiko 连接密码走环境变量 C4EAI_SSH_PASSWORD（代码里无硬编码）
→
② 远端备份先打包 c4eai-hub_backup_*.tar.gz
→
③ 排除上传排除 workspace/（用户数据）与 model_cache/
→
④ 重启＋验证Python 不热加载，改 .py 必须重启进程

内网免配置访问

  • dnsmasq 跑在 :53：c4eai / c4eai.lab → 自身，*.c4eai.lab 通配，上游转发 223.5.5.5，开机自启
  • 全组免配置需路由器 DHCP 下发该 DNS，兜底用项目根 C4EAI_hosts设置.bat
  • 端点一律 IP 直连（hub / qwen-local / start.bat 三处同步），组员零配置

前端防缓存三件套

  • 改 js/*.js 必须同步递增 index.html 里 <script ?v=> 版本号
  • 入口 / 与 *.html 均 no-cache（曾因漏设导致浏览器缓存旧 index.html，升级全部失效）
  • 页面不更新先 Ctrl+F5 再排查；验证以线上文件内容为准，不能只看版本号
双份同步铁律：技能 / 子智能体 / 后端改动，本地＋云端两份都要同步（skills 整目录＋改动的 py/js，勿碰 workspace 用户数据）并重启云端进程才生效。
Lessons

工程实践：几条踩出来的纪律

这些不是"最佳实践理论"，是项目里真实付过学费的教训

📏 上下文治理优先

附件注入、read_file、MinerU 长行 JSON —— 每一条进 prompt 的通道都要封顶。现在的三层防线：单条 8k ＋ 总量 30 万 ＋ read_file 20k 分页。

🔁 写后必须回读核对

批量迁移脚本"HTTP 200 ＝ 成功"是假象（云端跑旧代码 ＋ PUT 漏传字段）。铁律：写入后重新 GET 核对，只信回读结果。

🧪 验证纪律

scripts/check.sh 秒级静态自检（语法＋关键不变量）；行为验证用 Edge headless ＋ CDP 写断言脚本，跑完即删；只改前端也必须部署云端。

🔐 密钥与分发卫生

deploy_cloud.py 只读环境变量；分发清理清单剔除 workspace/、test_sse.py（含失效 key）；auth admin 走 env，代码本体无暗藏密钥。

Summary

总结与下一步

一句话总结

C4EAI = 双引擎 ReAct 智能体 ＋ 16 工具注册表 ＋ 可自我生成的技能系统 ＋ 云端共享 Wiki ＋ 六级权限，组内科研辅助与知识共享、50 人可用的科研工作台。

设计亮点

  • Hermes 式 file_id 引用 —— 历史不膨胀、附件即引用
  • 技能简列注入 ＋ 按需读取 —— token 效率与能力兼得
  • 子智能体硬约束（深度/并发/轮次/超时）—— 能力强但不失控
  • 权限、配额、文件沙箱三位一体 —— 多用户环境下的安全底座

待办 / 未决（诚实的清单）

  • 无自动化测试 —— 目前只有临时断言脚本；计划补最小测试套件（权限矩阵 / 多选上传 / 文件代理）
  • 旧数据库条目正文回填（权限改造前的占位符条目）
  • model_cache 不入库 → 新环境需联网重下 bge-small-zh
  • 本地实例的共享库读写依赖 hub_session token，过期需重新登录
